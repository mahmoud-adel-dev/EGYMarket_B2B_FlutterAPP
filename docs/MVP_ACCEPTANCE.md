# سيناريو قبول الـMVP

يُنفذ هذا السيناريو على بيئة Staging مستقلة ببيانات غير حقيقية. لا يعتبر الإصدار مقبولًا إلا إذا نجحت كل النقاط وسُجلت الأدلة.

## الإعداد

1. أنشئ مدير منصة وسجل دخوله إلى `/admin`.
2. اضبط رسم الطلب على 5000 قرش، وحساب تحصيل InstaPay للمنصة، وخطة اشتراك واحدة على الأقل.
3. سجل ثلاث منشآت: تاجر جملة، مشتري تجاري، وشركة شحن.
4. تحقق من البريد لكل حساب، وارفع مستندات التحقق، ثم اقبلها من لوحة الإدارة.
5. أنشئ فاتورة اشتراك لكل منشأة، ارفع إثباتها، واقبلها من لوحة الإدارة.

## البيع والشراء

1. يضيف تاجر الجملة حساب استلام محليًا ومنتجًا بسعر صحيح بالقرش، حد أدنى وكمية مخزون وشرائح أسعار.
2. تضيف شركة الشحن حساب استلام وتعريفة تغطي محافظة البائع ومحافظة المشتري.
3. يضيف المشتري كمية تحقق الحد الأدنى إلى السلة، ويختار الشحن، ثم يرسل طلب الشراء.
4. تحقق أن قيمة الصنف احتسبت على الخادم حسب الشريحة، وأن السعر المرسل من العميل لا يؤثر في الإجمالي.
5. يقبل البائع الطلب. يجب حجز المخزون وإنشاء ثلاثة التزامات فريدة:
   - رسم منصة = 5000 قرش.
   - قيمة البضاعة لصالح البائع.
   - قيمة الشحن لصالح شركة الشحن.
6. يرفع المشتري إثباتًا لكل التزام. يؤكد المدير رسم المنصة، والبائع البضاعة، وشركة الشحن الشحن.
7. لا ينتقل الطلب إلى `preparing` إلا بعد تأكيد الالتزامات الثلاثة.
8. أنشئ طلبًا آخر ولا ترفع أي إثبات، وقدّم وقت استحقاقه في بيئة الاختبار ثم شغّل مهمة الصيانة. يجب إلغاؤه وتحرير المخزون. لا يجوز الإلغاء الآلي إذا وُجد إثبات قيد المراجعة أو دفع مؤكد.
9. ينفذ التسلسل: `preparing` ثم `ready_for_pickup` ثم `in_transit` ثم `delivered` ثم `completed`.
10. لا يخصم المخزون نهائيًا إلا عند تأكيد الاستلام، وتظل الكمية محجوزة قبل ذلك.

كرر الاختبار باختيار استلام المشتري بنفسه. يجب إنشاء التزامين فقط وعدم السماح لشركة شحن بالتصرف في الطلب.

## اختبارات الفشل والأمان

- مستخدم من منشأة رابعة لا يستطيع قراءة أو تغيير الطلب أو إثباتاته.
- المشتري لا يستطيع تأكيد إيصال البائع أو المنصة، والبائع لا يستطيع تأكيد رسم المنصة.
- لا يمكن للبائع قبول طلب دون حساب استلام، ولا يمكن التداول باشتراك منتهٍ.
- لا يقبل إثبات دفع بطريقة غير مفعلة عند المستفيد.
- لا يمكن القفز بين حالات الطلب أو الإلغاء الآلي بعد بدء التحضير.
- فتح نزاع يجمد التزامات الدفع ذات الصلة ويظهر في لوحة الإدارة.
- تعطيل مستخدم أو تغيير `session_version` يبطل جلسة NextAuth الحالية.
- اختبار الاستعادة من نسخة MongoDB على قاعدة مستقلة ينجح.

## بوابة الإطلاق

- `npm audit` بلا ثغرات معروفة، و`npm run lint && npm test && npm run build` ناجحة.
- `flutter analyze && flutter test` ناجحة، وبناء Android Release موقّع ناجح.
- HTTPS وشهادته والتنبيهات والنسخ الاحتياطي والمهمة المجدولة تعمل.
- البريد وCloudinary وحسابات التحصيل الحقيقية مجربة بمبالغ صغيرة.
- الوثائق القانونية والضريبية معتمدة، وفريق الدعم يعرف إجراء النزاعات واسترجاع الأموال.
